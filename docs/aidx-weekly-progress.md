## 5. この進捗表の更新ルール

1. **発行したら** README.md の「📊 発行履歴」に1行追記する
2. **課題が片付いたら**「4. 残課題」から削除し、「3. 完了済み」に1行で記録する
3. **仕様を変えたら** SKILL.md を先に直し、このファイルの「2. 運用ルール」に反映する
4. 冒頭の「最終更新」日付を必ず書き換える
5. **更新したら** `/docs/` の実ファイルとプロジェクトナレッジの両方を差し替える（ナレッジは手動同期のため、片方だけ直すと古い前提で回答される）
6. **仕様の詳細はこの進捗表に書かない。** 「何が完了したか」＋正本ファイルへの参照に留める。判定基準や手順を要約して転記すると、正本を直したときにこちらが古くなり、逆向きのずれが起きる

| 内容 | 正本 |
|---|---|
| ニュースレターの仕様 | `SKILL.md` |
| 発行前監査の判定基準 | `docs/pre-publish-audit-prompt.md` |
| ファイルの役割・Git運用 | `CLAUDE.md` |
| 作業の経緯・Phase記録 | `work-log.md` |

### プロジェクトナレッジの差し替えタイミング

リポジトリとナレッジは自動同期しない。下表のタイミングで手動差し替えを行う。

| タイミング | 差し替えるファイル |
|---|---|
| **毎週の発行後**（進捗表を更新したとき） | `aidx-weekly-progress.md` |
| **SKILL.md を変更したとき** | `SKILL.md` |
| **CLAUDE.md を変更したとき** | `CLAUDE.md` |
| **メトリクスを記録したとき**（月初） | `seo-metrics.md` |
| **editor-comment-rules.md を変更したとき**（各号の是正が完了するたび） | `editor-comment-rules.md` |

`editor-comment-rules.md` は是正作業のたびに判断基準が増えるため、
更新頻度が高い。古い基準のままだと、次のチャットで確立済みの判断が
効かなくなる（例：Vol.10 で確立した項目13「判断基準を満たしている
箇所は変えない」）。

差し替え手順：プロジェクト設定のコンテキストで**対象ファイルを削除 → 更新版をアップロード**。同名での上書きはできない。

**なぜ必要か：** ナレッジが古いままだと、次のチャットで「Vol.25は未発行」「sitemapは29URL」といった古い前提でClaudeが回答する。Task 0 で削除した陳腐化SKILL.md（同名スキルの誤読込）とまったく同じ構造の事故なので、仕組みで防ぐ。
